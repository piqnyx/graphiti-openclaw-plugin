# Buffer System — Система буферов для Graphiti Plugin v0.2

_Документ фиксирует все решения по архитектуре буферов. Обновляется по ходу обсуждения._

---

## Общая модель

```
Agent (main / igor / ...)
├── group_id = agent_id (жёстко, из плагина)
├── Session 1 (диалог в UI / Telegram / ...)
│   └── Buffer [текущий, лимит N=50]
├── Session 2 (другой диалог)
│   └── Buffer [текущий, лимит N=50]
└── ...
```

Очередь агента (FIFO):
```
┌──────────────────────────────────────────────┐
│ head                                  tail   │
│ [ oldest → → → → → → → → → → newest ]       │
│  ↑ process here           ↑ add here        │
└──────────────────────────────────────────────┘
```

Люди встают в хвост (tail), уходят из головы (head). Как очередь к кассе.

## Буфер (Buffer)

**Что это:** Аккумулятор сообщений из одной сессии (одного диалога). Каждый буфер привязан к конкретной сессии и живёт своей жизнью.

**Структура:**
```typescript
interface Buffer {
  sessionKey: string;        // ключ сессии = saga ID для Graphiti
  messages: Message[];       // накопленные сообщения
  createdAt: number;         // timestamp создания буфера
  lastActivityAt: number;    // timestamp последнего сообщения
}
```

**Почему нет `agentId` / `groupId`:** Буфер всегда живёт внутри контекста агента. Агент знает свой `agentId` = `group_id`. Дублировать в буфере нет смысла — при processинге агент просто подставляет свой ID.

**Почему `sessionKey` нужен:** Используется как `saga` в Graphiti. Каждая сессия (диалог) = одна сага. Это позволяет потом на графе видеть из какого диалога было сказано то или иное. Сага связывает все эпизоды из одного диалога в единую цепочку.

**Лимиты (из конфига):**
- `bufferLimit`: 50 сообщений (минимум 30)
- `bufferTimeout`: 15 минут по умолчанию (900 секунд, минимум 30 секунд)

**Eligibility (минимум для эпизода):** (решено 2026-08-14, п.1)
- Эпизод попадает в очередь только как пара user+assistant (решено 2026-08-14, Q3):
  - `extractCompletedTurn` захватывает **единый блок**: последнее user-сообщение + ответ ассистента ПОСЛЕ него.
  - Если после user нет ответа бота — `extractCompletedTurn` возвращает `null`, в буфер **ничего не попадает**.
  - Как только бот ответил — в буфер попадает **и user, и ответ бота** вместе (не только сообщения после ответа).
  - Итог: в буфере никогда нет одиночного user без ответа — Graphiti не получает бессмысленные для поиска сущностей эпизоды.
- Буфер с **меньше чем 2 сообщениями** НЕ уходит в очередь по таймауту.
- Пустой буфер живёт, ждёт второго сообщения.
- Одиночное сообщение (например, бот затупил и не ответил) — **не эпизод**, для Graphiti это мусор.
- Эпизод создаётся только когда в буфере **минимум 2 сообщения**.

**Триггер отправки в очередь:**

**Eligibility gate:** буфер уходит в очередь только если в нём уже **>= 2 сообщений**. Если буфер содержит 0 или 1 сообщение — он НЕ отцепляется по таймауту, а продолжает ждать. Первое сообщение всегда просто добавляется в буфер, никаких триггеров.

Проверяется **перед добавлением** каждого нового сообщения:

1. **Лимит заполнен** → `messages.length >= bufferLimit` →
   - Отправить текущий буфер в хвост очереди агента
   - Создать новый пустой буфер для этой сессии
   - Добавить сообщение уже в новый буфер
   - Старый буфер побежал в очередь

2. **Таймаут сработал** → `now - lastActivityAt >= bufferTimeout` →
   - Отправить текущий буфер в хвост очереди агента
   - Создать новый пустой буфер для этой сессии
   - Добавить сообщение в новый буфер

**Про таймаут — ключевое:** Таймауту **плевать** что происходит в UI. Пользователь может:
- Удалить диалог — буфер живёт своей жизнью, тикает, потом уходит в очередь
- Отойти от компа — буфер считает время последней активности
- Переключиться на другой диалог — таймаут старого диалога продолжает тикать
- Писать в другом диалоге — это не влияет на буфер первого

У нас **своя структура данных**, плагин просто наталкивает в неё сообщения. UI — это визуал, буфер — это аккумулятор.

## Очередь (Queue)

**Что это:** FIFO-очередь заполненных буферов одного агента, ожидающих обработки.

**Одна очередь на агента.** Каждый агент (main, igor, ...) имеет свою очередь.

**Структура записи:**
```typescript
interface QueueEntry {
  buffer: Buffer;            // заполненный буфер
  enqueuedAt: number;        // timestamp попадания в очередь
}
```

**Почему не одна общая очередь на всех агентов:**
- Изоляция: ошибка в одном агенте не блокирует другие
- Проще: не нужно маршрутизировать по group_id
- Хронология: FIFO строго внутри одного агента

**Почему не отдельная очередь на каждую сессию:**
- У каждой сессии свой буфер, но очередь общая на агента
- Сессии внутри агента processятся последовательно (хронология)
- Одна структура данных проще чем N очередей

**Связь буфер ↔ сессия ↔ saga:**
- Буфер привязан к сессии через `sessionKey`
- При processинге `sessionKey` передаётся как `saga` в Graphiti
- Все эпизоды из одного диалога связаны в Graphiti через saga

## Движок (Processing Engine)

**Что это:** Фоновый таймер, который проверяет все буферы и processит очередь.

**Интервал проверки:** Равен внутренней константе = минимальному валидному `bufferTimeout` = **30 секунд**. См. раздел «Конфигурация» — `checkInterval` НЕ публичный параметр, это константа. Проверяльщик тикает каждые 30 секунд и перебирает все активные буферы всех агентов.

**Порядок проверки:**
1. Перебрать все активные буферы всех агентов
2. Для каждого: `now - lastActivityAt >= bufferTimeout`?
3. Если да → отправить буфер в хвост очереди агента
4. Взять из головы очереди → processить

**Processинг одного буфера:**
1. Взять `QueueEntry` из головы очереди
2. Вызвать MCP `add_memory`:
   - `group_id` = агентский `group_id`
   - `episode_body` = JSON из `entry.buffer.messages`
   - `source` = `"json"`
   - `saga` = `entry.buffer.sessionKey`
   - `reference_time` = `entry.enqueuedAt` (момент ухода буфера в очередь, ISO-8601)
3. MCP возвращает `queued for processing` — **не ждём** завершения
4. Удалить entry из головы очереди
5. Взять следующий

**Модель процессинга очереди (решено 2026-08-14, п.6):**
- За один тик движок processит очередь агента **до опустошения** (не по одному буферу за тик).
- С `await` между запросами: пока в очереди агента есть entries — берём из головы, шлём, ждём ответ MCP, удаляем, берём следующий.
- Это экономит тики и не задерживает очередь: при быстром MCP вся очередь уходит за один проход.

**Параллелизм:**
- Внутри одного агента — последовательно (FIFO, строго по порядку)
- Между агентами — параллельно (у каждого агента свой processing slot)

## Обработка ошибок

**При ошибке MCP:**
- Логируем ошибку (детали: buffer, session, ошибка)
- Уведомление в UI (всплывающее сообщение, см. ниже)
- Буфер **не возвращается** в очередь (карусель не нужна)
- Буфер удаляется — сообщения потеряны для Graphiti

**Почему не retry / не возврат в хвост:**
- Если буферу отказали N раз — проблема скорее всего в данных, не во времени
- Возврат в хвост может нарушить хронологию (другие буферы уже processились)
- Если проблема системная (MCP упал) — пострадают все буферы, retry не поможет
- Пользователь должен знать что что-то не так

**Механизм уведомлений:**
- Нужно найти в openclaw-src как вызываются всплывающие уведомления (notification toasts)
- Пример: при переключении reasoning level для моделей без поддержки — приходили красные всплывашки над чатом
- TODO: найти API для notification toasts в OpenClaw
- Fallback: логирование + статус в session status

## Edge Cases

### Пользователь ушёл из диалога
- Буфер считает `lastActivityAt` = последнее сообщение
- Через `bufferTimeout` таймаут сработает → буфер уйдёт в очередь

### Пользователь переключился на другой диалог
- Таймаут старого диалога продолжает тикать
- Новый диалог получает свой буфер

### Удаление диалога в UI
- Буфер живёт своей жизнью, не зависит от UI.
- Удаление диалога **не удаляет сообщения из буфера** — что попало в буфер, гарантированно попадёт в Graphiti.
- Через `bufferTimeout` уйдёт в очередь само, по таймеру.
- Никаких принудительных сливов при удалении сессии не делаем (лишний код, лишнее поле для ошибок). (решено 2026-08-14, Q1)

### Одновременное заполнение двух буферов
- Оба уходят в хвост очереди (FIFO по времени заполнения)
- Processятся последовательно

### Ошибка MCP
- Лог + уведомление в UI
- Буфер удаляется (не возвращается в очередь)
- Пользователь видит что что-то пошло не так

### Restart плагина
- Активные буферы: теряются (in-memory)
- Очередь: теряется (in-memory)
- **В будущем:** persistence (сохранять на диск)

## Конфигурация

```typescript
interface BufferConfig {
  bufferLimit: number;       // минимум 30, по умолчанию 50
  bufferTimeout: number;     // в секундах, минимум 30 (30 сек), по умолчанию 900 (15 мин)
}
```

**`checkInterval` НЕ публичный параметр конфига.** (решено 2026-08-14, п.4)
- Единственный публичный параметр интервала — `bufferTimeout` (интервал отцепления буфера и отправки в очередь). Он идёт в конфиг плагина.
- `checkInterval` (интервал проверки, какие буферы пора отцеплять) — **внутренняя константа**, равна минимальному валидному `bufferTimeout` = **30 секунд**. Внутри кода конвертируется в мс для таймера.
- Этой же константой валидируем конфиг: юзер НЕ может записать `bufferTimeout` меньше 30 сек.
- В конфиге указываем время **в секундах**; в коде при необходимости конвертируется (напр. в мс для таймера).

**Проверяльщик буферов — один общий на всех агентов** (решено 2026-08-14, п.2/п.4):
- У каждого агента своя очередь и свой processing slot (см. Движок), но таймер отцепления **один общий** — один тикер проверяет буферы всех агентов.
