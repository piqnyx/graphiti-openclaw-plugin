# Buffer System — Система буферов для Graphiti Plugin v0.2

_Документ фиксирует все решения по архитектуре буферов. Обновляется по ходу обсуждения._

---

## Общая модель

```
Agent (main / igor / ...)
├── group_id = agent_id (жёстко, из плагина)
├── Session 1 (диалог в UI / Telegram / ...)
│   └── Buffer [текущий, лимит N=50]
├── Session 2 (другой диалог)
│   └── Buffer [текущий, лимит N=50]
└── ...
```

Одна общая очередь на весь агент:
```
Agent Queue: [Buffer₁, Buffer₂, ...]
              ↑ head (process)
              ↑ tail (add)
```

## Буфер (Buffer)

**Что это:** Аккумулятор сообщений из одной сессии (одного диалога).

**Структура:**
```typescript
interface Buffer {
  sessionKey: string;        // ключ сессии в OpenClaw
  agentId: string;           // агент (main, igor, ...)
  groupId: string;           // = agentId, для MCP group_id
  messages: Message[];       // накопленные сообщения
  createdAt: number;         // timestamp создания буфера
  lastActivityAt: number;    // timestamp последнего сообщения
}
```

**Лимиты (из конфига):**
- `bufferLimit`: 50 сообщений (минимум 30)
- `bufferTimeout`: 15 минут (900 000 мс)

**Триггер отправки в очередь (проверяется ПЕРЕД добавлением сообщения):**
1. **Лимит заполнен** → `messages.length >= bufferLimit` → отправить буфер в очередь
2. **Таймаут сработал** → `now - lastActivityAt >= bufferTimeout` → отправить буфер в очередь
3. **Оба условия** — лимит приоритетнее (проверяется первым)

**После отправки:**
- Буфер отвязывается от сессии
- Сессии выдаётся новый пустой буфер
- Старый буфер попадает в хвост общей очереди агента

## Очередь (Queue)

**Что это:** FIFO-очередь заполненных буферов, ожидающих обработки.

**Структура:**
```typescript
interface QueueEntry {
  buffer: Buffer;            // заполненный буфер
  agentId: string;           // для выбора group_id
  groupId: string;           // = agentId, для MCP
  enqueuedAt: number;        // timestamp попадания в очередь
  attempts: number;          // счётчик попыток (для retry)
}
```

**Одна очередь на агента.** Каждый агент (main, igor, ...) имеет свою очередь.

**Почему не одна общая:**
- Проще: не нужно маршрутизировать по group_id
- Изоляция: ошибка в одном агенте не блокирует другие
- Хронология: FIFO строго внутри одного агента

**Почему не отдельная очередь на каждую сессию:**
- Проще: одна структура данных на агента
- Движок один на весь агент
- Сессии внутри агента и так не могут processиться параллельно (хронология)

## Движок (Processing Engine)

**Что это:** Фоновый таймер, который проверяет все буферы и processит очередь.

**Интервал проверки:** каждые 30 секунд (настраивается).

**Проверка:**
1. Перебрать все активные буферы всех агентов
2. Для каждого: проверить таймаут (`now - lastActivityAt >= bufferTimeout`)
3. Если таймаут сработал → отправить буфер в очередь агента
4. Взять из головы очереди каждого агента → processить (если не занят)

**Processинг одного буфера:**
1. Взять `QueueEntry` из головы очереди
2. Вызвать MCP `add_memory` с:
   - `group_id` = `entry.groupId`
   - `episode_body` = JSON с диалогом из `entry.buffer.messages`
   - `source` = `"json"`
3. Дождаться ответа (или не ждать — см. ниже)
4. Удалить entry из очереди
5. Если ошибка → увеличить `attempts`, вернуть в хвост (max 3 попытки)

**Параллелизм:**
- Внутри одного агента — последовательно (FIFO, строго по порядку)
- Между агентами — параллельно (у каждого агента свой processing slot)

**Ожидание ответа MCP:**
- MCP `add_memory` возвращает `queued for processing` — это асинхронно
- Движок **не ждёт** реального завершения обработки Graphiti
- Просто удаляет entry из очереди после успешного вызова
- Это позволяет processить следующий буфер сразу

## Формат episode_body для JSON

```json
{
  "user": "Вит",
  "assistant": "Краб",
  "conversation": [
    {"speaker": "Вит", "text": "..."},
    {"speaker": "Краб", "text": "..."}
  ]
}
```

**Имена speakers:** реальные (Вит, Краб), не generic (User, Assistant).

## Конфигурация

```typescript
interface BufferConfig {
  bufferLimit: number;       // минимум 30, по умолчанию 50
  bufferTimeout: number;     // в мс, по умолчанию 900000 (15 мин)
  checkInterval: number;     // в мс, по умолчанию 30000 (30 сек)
  maxRetries: number;        // max попыток на entry, по умолчанию 3
  retryDelay: number;        // в мс перед retry, по умолчанию 5000
}
```

## Edge Cases

### Пользователь ушёл из диалога
- Буфер остаётся активным с `lastActivityAt` = последнее сообщение
- Через 15 минут таймаут сработает и буфер уйдёт в очередь

### Пользователь переключился на другой диалог
- Буфер старого диалога: таймаут продолжает тикать
- Буфер нового диалога: начинает заполняться

### Одновременное заполнение двух буферов
- Оба уходят в очередь (FIFO по времени заполнения)
- Processятся последовательно (внутри одного агента)

### Ошибка MCP при processинге
- Retry до `maxRetries` раз
- Если все попытки провалились → логируем, удаляем entry (не блокируем очередь)

### Restart плагина
- Активные буферы: теряются (in-memory)
- Очередь: теряется (in-memory)
- **В будущем:** persistence (сохранять буферы и очередь на диск)
